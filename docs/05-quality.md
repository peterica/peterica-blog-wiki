# 05. 품질 검증과 교정

## Rubric 기반 자동 평가

LLM이 생성한 결과물을 그대로 쓰면 안 된다. `evaluate.py`가 각 레코드를 Rubric으로 검증한다:

| 항목 | PASS 조건 |
|---|---|
| 필수 필드 | id, title, url, summary, tags 모두 존재 |
| 요약 길이 | 120~500자 (config.yaml에서 조정 가능) |
| 요약 문장 수 | 2~6문장 (한국어 종결어미 기반 카운터) |
| 태그 | 3~7개, kebab-case, 중복 없음 |
| 날짜 | ISO-8601 (YYYY-MM-DD) |

### 한국어 문장 카운터의 함정

초기 문장 카운터는 마침표(`.`)로 분리했다. 그런데 `tar.gz`, `hbase-env.sh`, `OpenJDK 8.0`의 마침표도 문장으로 카운트되어 PASS율이 78%까지 떨어졌다.

해결: 한국어 종결어미 패턴(`다.`, `요.`, `죠.` 등) + 공백/문말 조합으로 변경:

```python
KO_SENT_END_RE = re.compile(r"[가-힣]\.(?:\s|$)|[!?](?:\s|$)")
```

이 정규식은 "한글 + 마침표 + 공백 또는 문말"만 문장 종결로 인식한다.

## 품질 정규화

Rubric FAIL의 주요 원인:

1. **요약 길이 부족 (30%)**: qwen3:8b가 120~140자 구간에 많이 분포. 임계를 150 -> 120으로 조정.
2. **태그 대소문자 (11건)**: `SQL-문제` 같은 대문자 태그. lowercase 정규화 스크립트 적용.
3. **boilerplate**: "핵심 키워드는 ... 입니다" 같은 LLM 정형 문구. 자동 제거.

정규화 후: **63.8% -> 90.9% -> 98.2%** (970/987 PASS)

## 위키 품질 평가

`wiki_evaluate.py`는 concept/entity 페이지의 구조적 품질을 검증한다:

- **필수**: frontmatter 완전, type 정확, "한 줄 정의" 존재, 포스트 참조 존재
- **권장**: related 링크, 본문 200자 이상, TODO/placeholder 없음
- **Confidence**: 필수 + 권장 3개 = high, 필수 + 권장 1개 = medium, 그 외 = low

결과: 183/183 (100%) PASS, high confidence 98.4%.

## 위키링크 정합성

LLM이 포스트를 `[[722]]`로 참조했는데, 실제 파일명은 `0722-slug.md`. Obsidian은 파일명 기준으로 링크를 해석하므로 깨진다.

해결: ID -> 파일명 매핑 JSON을 생성하고, 815건의 숫자 링크를 일괄 교정:

```python
# [[722]] -> [[0722-Linux-ssh-keygen-명령어를-사용하여-SSH-키를-생성]]
new_content = re.sub(r"\[\[(\d+)\]\]", replacer, content)
```

두 번째 문제: LLM MOC 오분류 41건(27.2%). SSO 글이 "프롬프트 엔지니어링"에 연결. 키워드 기반 재분류 + MOC 교차 검증으로 30건 무효 참조 제거.

## 교훈

- 자동 검증 스크립트 없이 LLM 산출물을 쓰면 카테고리 오분류(27%), 위키링크 깨짐(815건), 무관한 참조(30건)를 놓친다.
- Rubric 기반 평가 + MOC 교차 검증의 조합이 효과적이다.
- 품질 기준은 config.yaml에서 프로젝트별로 조정 가능하게 설계해야 한다.
